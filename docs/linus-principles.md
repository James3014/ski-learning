# Linus Principles

## 核心使命
以 Linus 的好品味、實用主義與『Never break userspace』為根基，在決策與 review 時先問三個問題、再走五層思考，所有變更都必須圍繞清楚的資料結構與最小化特殊情況。

## Linus 的三個問題
1. 這是個真問題還是臆想出來的？
2. 有沒有更簡單的方法？
3. 會不會破壞既有使用者空間？

> 每次開新 Issue、寫新 feature 前都要自問一次，若沒有明確 answer 就暫停。

## 五層分析架構
1. **資料結構分析**：核心資料是什麼？誰持有、誰改？資料流向清楚就簡潔。只有一組 data model，UI 只 render 那一份。
2. **特殊情況辨識**：所有 if/else 都要被質問；能否把分支搬到資料層或用 default 去掉？
3. **複雜度審查**：超過 3 層縮排警報，重構成 helper 或拆流程。好 Code 不是多加抽象，而是先把問題說清楚。
4. **破壞性分析**：列出會受影響的功能、資料契約；確保所有舊有 API 仍舊工作。沒有向後相容就不能合併。
5. **實用性驗證**：這問題真在「使用者那邊」？產生的複雜度 VS 解決的痛點是否成比例？若太貴就留著，別過度優化。

## Review 守則
- **數據先於實作**：檢查 `data structure` 是否表現清楚；若還在 UI 加 if/else，那資料設計沒做好。
- **特殊 case 消除**：每個分支都要能用 default 處理，否則要有測試證明存在性。
- **複雜度下限**：一個函數最多三層縮排；若需更多，拆成 helper 並加測試。
- **破壞性檢查**：PR 說明需要列出「會修改 Who」「可能 break 的 contracts」，沒寫就退回。
- **實用性回饋**：批評要號稱針對技術；不能友善就模糊，直接指出為何這樣做是個 bug。

## 當前流程結合五月指令
1. 每個 Issue 都要貼上三個問題的答案。
2. PR template 附上五層問題回覆欄位。
3. 設備來自 UI 或資料源的特殊要求都要在 `specs` 章節寫入，保證 review 時能追溯。
